The system

Three kinds of people use one app. Everything is saved in the browser they use, so two people can't share a case yet.

Architecture

Where each part runs. GitHub Actions builds the app, Vercel serves it, and the browser does everything else.

Context

The same system at the highest level: who uses it and what it touches outside.

Roles and screens

The Coordinator runs the case, the Hospital handles intake, and the family sees plain-language status and the map.

Patient journey

The full path from one referral to the last follow-up visit, including what happens when a hospital says no or a ride fails.

Referral status

The statuses a referral really moves through in the app. FLOATING is REJECTED in the code: the hospital said no and the patient chooses next. Choosing makes the referral SENT again in the same click. Recording the outcome goes straight to COMPLETED.

Ride status

Dispatch does request, assign and send in one click. Confirming arrival also closes the ride, even if nobody logged the pickup.

Barriers

A barrier is anything stopping the patient from getting there. Only transport barriers can be closed today.

42-day follow-up

Care continues after the hospital. The plan starts when the outcome is recorded, but nothing watches the due dates yet.

Effort against impact

Positions are my estimate, not a measurement.

Fix first: the gaps these changes left

  1. No alarm when an accepted patient never arrives. The clock stops once a hospital accepts, but this is the failure the product exists to catch. It needs a limit from a clinician. alarms.js
  2. A case that ends outside the network can't close. If a patient goes to a hospital not on Navexa, nobody can confirm arrival, so the case stays open and keeps alarming. recordPatientGoingElsewhere
  3. Roles are not enforced. "Hospital only" is true on screen, but the rules behind it don't check who is acting. It needs a real login. workflow.js
  4. Every hospital can open any case by ID. That's how walk-ins work, but a real system must check who is asking and log it. FacilityDashboard.jsx

Before the pull request

  1. Commit the redesign. All of it is uncommitted on feat/landing-redesign, which is also 1 merge commit behind upstream/main.
  2. Update dependencies. npm audit reports 9 issues: 8 moderate and 1 high in Vite. react-router is the one that reaches users. None come from zombie-mermaid.
  3. Turn on the undefined-variable lint rule. no-undef is off, so lint passed today on a page that used a variable that no longer existed.
  4. Add browser tests. The 116 tests cover rules and config. Nothing automatically clicks through the real screens.
  5. Write the README and clean up old docs. The README is one line. Older reports still claim a 95/100 score, describe removed features and link to d:/ paths.
  6. Finish the accessibility check. axe hasn't run, because its page script was blocked in this setup, and no real VoiceOver or TalkBack pass has happened.

Needs someone else

  1. Clinical review. An obstetrician and a neonatologist should check referral routing, bilirubin and blood pressure thresholds, and the follow-up schedule.
  2. A decision on patient addresses. The map shares only the hospital's location today. Drawing a route from home means sending the address to a map company.

Needed for real patients

  1. Real login and access control. Today anyone can pick any role, and the check runs only in the browser.
  2. A secure shared database. Patient data must leave browser storage, with an audit trail that can't be edited.
  3. Real SMS and calls. Alerts appear only inside the app.
  4. Real map data. Hospitals are fictional and pinned at area centres, the map draws no route, and van tracking is fixed text.
  5. Hospital record links and offline use. FHIR exchange and an offline mobile app are on the roadmap, and neither is started.
